## Problem Statement

The current Audiobookshelf mobile app looks dated and inconsistent, and its Nuxt 2/Capacitor presentation does not provide the native experience the owner wants on iPhone, iPad, and Android. A new Apple TV client exists, but its interface is a functional first pass and its live-server and physical-TV acceptance are incomplete.

The owner wants modern native apps across phone, tablet, and Apple TV, without losing any existing mobile capability or existing downloads and listening progress. The owner also wants an explicit second phase that replaces the legacy Vue/Nuxt client technology with a Next.js browser client. The existing Audiobookshelf server must remain usable throughout this migration.

## Solution

Deliver the migration in the owner's Audiobookshelf app fork with Apple, Android and Next.js implementation running in parallel in isolated worktrees, as authorized on October 1, 2026. Keep the original two-phase architecture and platform acceptance gates:

- **Phase 1:** Complete fully native SwiftUI apps for iPhone/iPad and Apple TV, including migration and physical-device acceptance, while a separate worktree implements and validates the Kotlin/Jetpack Compose Android app. Provide a consistent modern design while respecting touch, accessibility, and TV remote navigation. Achieve the applicable mobile parity baseline, with PDF, EPUB, MOBI/AZW3 and CBZ/CBR required under the October 3 amendment, before replacing it. Apple TV implements the features appropriate to a television rather than copying every mobile capability.
- **Phase 2:** Deliver a Next.js browser client against the existing Audiobookshelf server, carrying forward the modern design and relevant client capabilities. The existing Audiobookshelf browser interface remains available during phase 1. Native apps never depend on a new Next.js service to reach the user's server.

Build replacements alongside the legacy application. Internal milestones can demonstrate individual workflows, but an audio-only milestone is not the mobile replacement release; PDF and all other non-deferred capabilities remain required. Publish a platform parity matrix and migration evidence before cutover.

## Implementation Decisions

- **Confirmed parallel implementation:** On October 1, 2026, the owner authorized separate Android and Next.js agents to implement concurrently in isolated worktrees while Apple work continues. This overrides the earlier Apple → Android → Next.js implementation-start dependencies. Phase 1 remains native clients and phase 2 remains the browser migration. Each platform must independently pass its applicable acceptance and preservation requirements before replacing a working client; parallel development does not waive readiness or server compatibility checks.
- **Parity baseline:** Use upstream v0.14.2-beta at commit 7014e04e as the initial mobile feature baseline. Inventory actual behaviour by platform, including server permissions and feature availability, before implementation. Cover the entire current mobile app, not only the stories explicitly enumerated here. Later upstream changes enter through an explicit compatibility review rather than silently expanding or shrinking the baseline.
- **Release gate:** Maintain a platform parity matrix linking each baseline capability to an implementation and observable acceptance evidence. Every applicable mobile capability must pass before that platform replaces the legacy app. Missing baseline functionality cannot be waived as an audio-first release without an explicit scope change. Internal incremental builds are allowed.
- **Apple architecture:** SwiftUI interfaces with shared Apple API/domain, credentials, playback, progress, and applicable persistence capabilities. Keep TV layout and focus behaviour separate from mobile presentation. Extract useful existing Swift code and the new TV core behind cohesive interfaces rather than retaining Capacitor as the native shell.
- **Android architecture:** Kotlin with Jetpack Compose presentation and native playback/download/storage services. Separate reusable domain behaviour from activity, screen, and legacy bridge dependencies. Assess the existing ExoPlayer/media-session implementation as part of modernization; retain its supported behaviour when replacing the underlying service implementation.
- **Presentation ownership:** Library, item detail, search, collections/playlists, podcasts, downloads/local media, player, readers, account/settings, statistics, and diagnostics all receive native presentation. Native reading presentation must preserve currently supported formats, reader settings, and location semantics; document rendering is selected by format and validated against actual reading behaviour.
- **Platform core contracts:** UI issues commands and observes authoritative state. Playback, sleep timers, download tasks, and pending progress persist independently of screen lifetime. Screen dismissal is not session closure. Define interruption, route-change, background, termination, and explicit stop behaviour separately for mobile and TV rather than applying one blanket policy.
- **Progress contract:** Distinguish a media position from accumulated listening-time deltas. Persist pending progress before losing process state; acknowledge and retire reports only after successful server handling. Specify ordering, retries, and duplicate handling around the actual Audiobookshelf API so reconnects do not double-count listening time or overwrite a newer position. Keep audiobook, episode, and ebook locations distinct.
- **API compatibility:** Continue to use the existing Audiobookshelf HTTP and realtime contracts, modern refresh-token authentication and applicable legacy token support. Preserve local-network and reverse-proxy subpath operation. Do not introduce mandatory server schema changes or a replacement authentication service.
- **Cross-platform consistency:** Maintain versioned API contracts and shared fixture scenarios; generate clients where a reliable schema exists or is established and validated. Swift, Kotlin, and TypeScript remain separate implementations where platform behaviour requires it. Share semantic design tokens and behavioural expectations without forcing identical layouts or sharing native UI source across languages.
- **Authentication:** Keep native credentials in platform secure storage. Support existing mobile password and OpenID flows. Coordinate refresh operations and distinguish temporary transport failures from unrecoverable authorization rejection. A successful reauthentication must not silently discard recoverable listening state. Never log passwords, tokens, or private signing material.
- **TV scope:** Retain and improve the existing native TV foundation. Phase 1 TV acceptance covers remote-operated connection/sign-in, library browsing/search, book details, audiobook and podcast streaming/resume, multi-file playback, chapters, speed, system transport controls, and reliable progress persistence/sync. TV downloads, ebook reading, and other mobile-specific capabilities are not automatically required by mobile parity. Do not require an unsupported TV authentication flow or invent new server endpoints; document which server authentication modes the TV supports.
- **Design system:** Replace wooden shelves, bevelled dividers, glossy labels, and oversized branding with prominent cover art, clear typography, consistent spacing, restrained surfaces and accent colour, and an explicit primary-action hierarchy. Mobile uses touch-appropriate primary navigation and a persistent mini-player. TV uses remote-appropriate top-level navigation and visible focus. Preserve readable cover artwork and handle long titles, missing artwork, and large libraries.
- **Capability parity:** Preserve existing platform-specific casting, Android Auto, storage access, notifications/media controls, local-media workflows, and advanced preferences where supported today. Do not add a feature to another platform merely because it exists on one. Preserve available account/server-authorized actions rather than duplicating server administration.
- **Data migration:** Inventory native databases, local files, preferences, secure-storage entries, and ebook-location formats. Provide a versioned, resumable migration that validates copied or transformed data before retiring legacy data. Avoid mandatory redownloads and destructive cleanup before validation. Preserve unsent progress and separate data by server/account. Verify upgrade and recovery paths with production-shaped synthetic data.
- **App identity:** An in-place upgrade requires compatible app identifiers, signing, sandbox access, and secure-storage entitlements. A newly identified fork cannot assume access to the original upstream app's private storage. Distinguish migration from the existing locally signed fork from migration from the public upstream app; provide supported import/reauthentication paths or clearly document restrictions. Do not claim preservation where the OS prevents it.
- **Coexistence and cutover:** Keep legacy builds usable while native replacements are developed. Define backup, recovery, and rollback constraints for each supported upgrade path; do not assume an older binary can read a newly transformed database. Validate data preservation before distributing a replacement under an existing identity.
- **Phase 2 Next.js:** Use React/TypeScript and Next.js for a real browser client, not a new mobile WebView shell. Deliver actual server-connected workflows and the modern design, then retire the legacy Vue/Nuxt client from the fork's maintained replacement path once acceptance passes. Native apps are already independent of Nuxt/Capacitor after phase 1; phase 2 does not gate their release.
- **Browser compatibility and deployment:** The initial browser scope is the user-facing client behaviour from the app parity inventory where browsers can support it, not a rewrite of the upstream server's complete administration interface. Specify self-hosted deployment, server-address selection, authentication callbacks, CORS/origin rules, subpaths, and media reachability. Do not assume a cloud-hosted Next.js service can reach every user's LAN server. Never advertise native background playback, file access, or offline-download guarantees as equivalent browser capabilities without evidence.
- **Local-only builds and verification:** Build, test, sign, and package each client on the Studio using local tooling. Run the controlled server, fixtures, migration checks, and verification locally. Record reproducible commands and dependencies; do not require paid cloud builds, hosted CI, remote runners, hosted authentication, or a hosted intermediary. GitHub remains source and issue tracking, not a required compute platform.
- **Internal distribution:** Deliver directly installed native builds and a self-hosted Next.js client for internal use. Public releases, App Store/Play Store submissions, TestFlight, and paid cloud deployment are not completion requirements. Preserve identifiers, signing, sandbox compatibility, and recovery constraints even for internal distribution; reuse the existing developer setup.
- **Server release compatibility:** Record exact tested server versions and applicable capabilities. Before adopting a new upstream server release, run local compatibility journeys against the candidate for every completed client. When authentication, API, realtime, media, or progress behavior changes, adjust affected clients and verify regression evidence before upgrading the internal server. Extend the compatibility matrix as Apple, Android, and Next.js become available. Unknown future changes are maintenance work triggered by a concrete server release, not permission to install an unverified version automatically.
- **Delivery:** Implement in the owner's fork with reviewable changes and evidence. Preserve upstream history and license obligations. Keep the original maintainer's repository as the upstream reference. This issue is the approved migration specification and does not represent completed implementation.

## Testing Decisions

- **Confirmed primary seam:** Exercise an app-level user journey against a controlled Audiobookshelf-compatible server. Drive production screens and platform controls, and assert visible behaviour, actual media outcomes, persisted state, and the server's observed requests/progress. Use one shared scenario vocabulary and fixture server across platforms, with platform-specific runners, rather than inventing unrelated seams for each module.
- **Good tests:** Verify externally meaningful behaviour and failures, not component structure, internal method calls, or a mirrored implementation. A pretty screen, a successful build, or a mock invocation alone does not prove a playback, download, migration, or focus workflow works.
- **Prior art:** The TV core already has nine tests covering API/domain behaviour, and the TV smoke work ran production store/player code against an isolated HTTP fixture with synthetic accounts, 61 library items, multi-file audio, token expiry, and progress reports. Reuse those fixtures and contracts where applicable. Extend acceptance to real UI navigation because the existing smoke called production methods directly and did not prove physical-remote behaviour. Lexidraw's corpus/differential checks are reference ideas for equivalent contract or migration behaviour, not a dependency to import into this project.
- **Modules exercised:** Authentication and connection handling, API/domain adapters, library/search/detail presentation, native playback and system media integration, podcast sessions, progress synchronization, downloads/local storage, ebook readers, settings, migration, and TV navigation. Phase 2 exercises the browser client through the same server scenarios where applicable.
- **Normal journeys:** Sign in, select a library, search/paginate, open an item, play/resume, navigate away, background or lock a mobile device, use system controls, change chapters/speed, stop, and resume on another device. Cover books, podcasts, reading, playlists/collections, and supported account actions from the parity inventory.
- **Failure journeys:** Expired/rotated tokens, repeated refresh failures, temporary 403/404/5xx responses as interpreted by the endpoint contract, network loss and recovery, interrupted media requests, unsafe/unexpected URLs, missing covers, permission denial, unavailable content, and server capability differences. Assert that transient failures do not erase credentials or pending progress.
- **Playback journeys:** Multi-file boundaries, rapid consecutive seeks, end-of-book, end-of-episode, pause during preparation, speed changes, sleep timers, interruptions and route changes. Validate reported listening deltas and final position, including termination and retries, through the server fixture.
- **Offline and migration journeys:** Download, interrupt/restart, resume or retry, play with no network, terminate/relaunch, reconnect, and synchronize pending progress. Seed an old-version dataset with files, settings, credentials where accessible, and unsent progress; upgrade and verify actual file availability and correct positions without silent resets. Exercise interrupted migration, repeat execution, incompatible app identity, and the documented recovery path.
- **Reading journeys:** Real representative files for every current format, long documents, supported typography/navigation preferences, saved locations, legacy ebook-location conversion, offline modes where currently supported, and reading while audio plays. Assert that the same passage is resumed rather than only that a location field was copied.
- **Design and accessibility:** Check phone, tablet, and TV layouts with long titles, mixed cover shapes, missing content, loading/empty/error states, large text, screen-reader navigation, contrast, localization, reduced motion, and TV focus/back behaviour. Screenshot evidence complements behavioural tests; it does not replace them.
- **Real devices:** Validate actual background playback, audio routes, headset/Bluetooth and system media controls, casting and Android Auto where applicable, and a paired physical Apple TV's remote navigation, installation, and playback against a real server. Simulator verification alone cannot close those acceptance items.
- **Phase 2:** Verify browser sign-in, server selection/subpaths, search/browse, media playback and supported reading/progress behaviour, reload/session recovery, keyboard/accessibility navigation, and documented deployment/origin cases. Test explicit capability fallbacks rather than assuming native parity.
- **Red-first practice:** For new automated tests, first demonstrate the relevant failure before implementing the behaviour. Avoid low-value implementation-mirroring tests and green-only test backfills.
- **Completion evidence:** An internal replacement requires applicable parity rows to pass, reproducible builds, data-migration acceptance, real-device evidence for platform integrations, and documented remaining platform limitations. Builds and smoke checks already completed for the old architecture are not evidence that the replacement passed.

## Out of Scope

- React Native as the phase 1 mobile UI architecture, or replacing Nuxt with Next.js inside a Capacitor mobile shell.
- Replacing the Audiobookshelf server, its database, or its identity provider; requiring a new hosted backend to use native apps.
- Making an incomplete audio-only native app the replacement release.
- Replacing the working browser client before Next.js phase 2 acceptance. Parallel implementation is authorized.
- Automatically requiring downloads, ebook reading, or every mobile management action on Apple TV.
- Adding new car integrations or other platform features that are not part of the existing mobile parity baseline.
- Rebuilding all upstream server administration capabilities in the phase 2 browser client.
- Promising cross-sandbox access to another app's private files, credentials, or database, or a rollback path the platform/signing/data format does not support.
- Public app-store releases, TestFlight distribution, paid cloud build/CI/hosting pipelines, and mandatory hosted services.
- Automatically upgrading the live server, or treating specification publication as successful implementation or internal replacement.
