# Android cancelled-download recovery (#42, PR #140)

Both Cancel controls originally called `Downloads.delete`, deleting the durable record and completed audio/PDF parts. Cancel now persists a retryable stopped record and retains media; Discard/Remove remains explicit deletion. The cancellation explanation falls back to English in other locales. Existing `retry` and fresh-request Save-again queue transitions already retain matching completed parts, so Android did not share Apple's stale queue-state defect fixed in #127.

Independent review of `c2258851` found that cancellation still stopped binding to the HTTP call after headers. A cancelled worker could keep reading/writing the same `.part` file as its immediate retry. The corrected downloader retains a cancellation child until response close, cancels the active call directly on Cancel, and checks cancellation before/after blocking body reads. Each record has exclusive attempt ownership through IO cleanup. Cancellation invalidates that ownership generation; state updates and file publication check the generation under the same boundary as Cancel. A new worker for that record waits for the old attempt to exit, while unrelated download records retain the existing three concurrent transfer slots.
