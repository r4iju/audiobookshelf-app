## Supported contracts

Apple describes Automatic Screen Capture as controlling whether the UI Automation runner captures screenshots while running tests, separately from deleting screenshots for passing tests. Preferred Capture Format selects video or screenshots. Therefore selecting screenshots alone is insufficient, and capture OFF is a supported control rather than merely an absent-artifact inference. [Apple test-plan documentation](https://developer.apple.com/documentation/xcode/organizing-tests-to-improve-feedback)

Apple Xcode15 release notes also document disabling default automatic screen recordings in the test plan or scheme Test action options. This predates the old Xcode16.2 acceptance controller. [Apple Xcode15 release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-15-release-notes)

## Remaining audit-specific uncertainty

Apple WWDC23 shows that an accessibility audit fails natively when issues are found and demonstrates opening an element screenshot from an audit issue. It describes the issue handler as a filter for ignoring issues, and supplies no screenshot-disable option or explicit relationship between these issue images and the runner automatic-capture setting. [Apple accessibility-audit session, transcript around3:00–6:00](https://developer.apple.com/videos/play/wwdc2023/10035/)

Installed public SDK27 headers agree. `/Applications/Xcode.app/Contents/Developer/Platforms/iPhoneSimulator.platform/Developer/Library/Frameworks/XCUIAutomation.framework/Headers/XCUIApplication.h143–149` exposes audit types and an optional issue handler; each native issue is recorded as an XCTIssue. Returning YES prevents issue recording, which would violate the required all-issues contract. `XCUIAccessibilityAuditIssue.h` exposes only element, compactDescription, detailedDescription and auditType, with no image flag. No control here allows retaining unchanged native failures while suppressing their internal images. [Public audit API](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/performaccessibilityaudit(for:_:))

Apple documents issue attachments and general XCTAttachment lifetimes. The public lifetime API concerns keeping/discarding attachments after a test, and does not give an audit image-creation prevention contract. This is a different API from the scheme automatic-capture setting; its retention wording does not invalidate that scheme control. [Apple attachment documentation](https://developer.apple.com/documentation/xctest/adding-attachments-to-tests-activities-and-issues)

Historical exact strict combined RED2 at `/tmp/native239-contrast-detail.json` hasMediaAttachments=true and App Screenshot/Element Screenshot PNG names. It proves that the old configuration generated issue images; it does not prove the new capture-OFF configuration will do the same. The older preflight statement that only a policy allowing framework images can reopen audit execution is superseded as a categorical conclusion: the newer public control exists, while its audit-specific scope is unresolved. No screenshot or attachment payload was viewed/exported during this task.

Absent exported or retained images cannot prove zero creation. Nor can setting attachment retention, deleting images after creation, removing issue attachments, returning YES and rebuilding assertions, or reducing audit types establish the requested unchanged/no-capture seam. None was attempted.

## Public issue/context hooks do not establish prevention

Public `XCTestCase.record(_:)` takes an already supplied XCTIssue. `XCTMutableIssue.attachments` changes its array of supporting XCTAttachment objects; `add(_:)` adds supporting data. These are recording/attachment APIs, not documented pre-capture veto hooks. Installed XCTestCase.h and XCTIssue.h expose recording and mutable attachments with no audit image-creation callback. Neither the inspected primary docs nor these headers explicitly guarantees that an override, observer, context hook, or attachment-array change runs before framework screenshot creation. Removing attachments here could change recorded diagnostics and could occur after creation, so it is not a supported solution to this requirement. [Apple record API](https://developer.apple.com/documentation/xctest/xctestcase/record(_:)), [Apple mutable issue attachments](https://developer.apple.com/documentation/xctest/xctmutableissue/attachments)

This is a lack of documented prevention capability in the inspected public surface, not a claim of technical impossibility.
