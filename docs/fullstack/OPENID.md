# OpenID operation and migration contract

The configured public URL is authoritative for provider callbacks. Host and forwarded headers never construct a callback. It must include this image's compiled base path. Browser callbacks and native custom-scheme callbacks require exact configured allowlist entries. Cookies are HttpOnly, SameSite=Lax, scoped to the OpenID routes and Secure on HTTPS. Development HTTP/private hosts require an explicit LEAFWAKE_OPENID_ALLOWED_HOSTS operator setting; discovery and every backend request pin validated DNS addresses and bound response size/time. Production endpoints use HTTPS.

The existing clients retain their PKCE verifier and server cookie. The server stages the actual provider code privately, returns an opaque one-use handoff code to the client and exchanges only with matching cookie, state and verifier. Pending flows are encrypted and durable for ten minutes. Provider discovery, signed ID token, audience/issuer, nonce and PKCE validation use pinned openid-client 6.8.8. The actual authorization-response issuer is retained and checked against the discovered issuer. Secret-bearing configuration and flow data use AES-256-GCM with a purpose-derived private key; APIs return only hasClientSecret. Setting changes invalidate pending flows.

Accounts are bound to the discovered issuer and subject. New registration is opt-in and creates ordinary accounts with no update/delete/upload authority. Existing local usernames and email claims are never automatic account links. Existing mapped accounts survive disabled registration, and current account activation is rechecked when issuing sessions. Local refresh/session revocation contracts remain in force.

Original account authOpenIDSub values and provider settings are currently explicitly rejected by account migration inspection. Complete migration #172 must import validated issuer/subject mappings with original account IDs and validate provider settings before clearing that blocker. Group/advanced permission claims, email/username auto-matching, manual endpoint overrides and unsupported original provider policies must be reported and require explicit replacement mapping. They cannot be silently enabled or counted as migrated. The original snapshot remains read-only. Private signing/settings keys must remain with the persistent data volume; portable backup/key packaging is part of #170.

Sources: [openid-client documentation](https://github.com/panva/openid-client/blob/main/docs/README.md), [authorization code grant checks](https://github.com/panva/openid-client/blob/main/docs/functions/authorizationCodeGrant.md).
